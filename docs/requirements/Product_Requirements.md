# 1. Vision проекта

## 1.1. Описание продукта

AnonPulse — платформа анонимной обратной связи для образовательной среды. Преподаватели создают опросы, содержащие один или несколько вопросов с вариантами ответа, и публикуют их по ссылке. Студенты открывают опрос без регистрации и отправляют ответы анонимно. Пользователи могут просматривать агрегированную статистику и историю, а преподаватели — публиковать решения, принятые по итогам обратной связи.

## 1.2. Vision Statement

Для студентов и преподавателей, которым важно безопасно и системно обсуждать качество учебного процесса, AnonPulse — платформа анонимных опросов, позволяющая собирать ответы на один или несколько вопросов, анализировать общие результаты и фиксировать последующие действия. В отличие от устных обсуждений и разрозненных форм, сервис объединяет доступ к опросу по ссылке, анонимное голосование, статистику, историю и публикацию решений.

## 1.3. Проблема и ценность

Студенты могут избегать открытой критики из-за опасения негативной реакции. Из-за этого преподаватель получает неполную картину и не всегда понимает, какие аспекты занятий требуют изменений. AnonPulse упрощает отправку мнения и помогает преподавателю принимать решения на основе агрегированных данных.

## 1.4. Основной сценарий

1.  Преподаватель создаёт опрос, добавляет один или несколько вопросов и варианты ответа к каждому вопросу.

2.  Преподаватель публикует опрос и передаёт студентам прямую ссылку.

3.  Студент открывает ссылку без входа в аккаунт, выбирает ответы и отправляет их.

4.  Система проверяет возможность участия, сохраняет ответы отдельно от браузерного токена и показывает подтверждение после успешного сохранения.

5.  Преподаватель закрывает опрос, просматривает агрегированные результаты и при необходимости публикует решение.

Доступ к статистике: студент видит агрегированную статистику по опросу только после его закрытия преподавателем. До закрытия опроса студенту доступна только форма голосования. Преподаватель может видеть результаты в реальном времени. Ограничение статистики обеспечивается на уровне API: публичный эндпоинт не возвращает агрегированные данные открытого опроса, проверка прав преподавателя выполняется отдельно.

Поведение закрытого опроса: при открытии закрытого опроса публичный API возвращает код 409 Conflict. Фронтенд перехватывает этот код, отображает статус «Опрос завершён» и опубликованное решение преподавателя (если оно есть). Форма голосования при этом неактивна, кнопка «Отправить» заблокирована.

Авторизация преподавателя: в первой версии (MVP) самостоятельная регистрация преподавателей не предусмотрена. Учётная запись преподавателя создаётся администратором системы (или через seed-данные) заранее. Авторизация преподавателя осуществляется по логину и паролю. Студенты проходят опрос по прямой ссылке без регистрации.

Ограничения доступа и анонимности: на первом этапе прямая ссылка является единственным условием доступа — любой, кому её передали, может открыть опрос; принадлежность к конкретной учебной группе не проверяется. Браузерный токен с хешированием SHA-256 препятствует повторному участию в том же опросе из того же браузера при сохранённой cookie, но не гарантирует один голос на человека. Повторное участие возможно из другого браузера или после удаления cookie. Поэтому в документации не заявляется абсолютная уникальность участника.

# 5. Product Backlog: User Stories и критерии приемки

Формат историй: «Как \[роль\], я хочу \[действие\], чтобы \[ценность\]». Story Points (SP) — предварительная относительная оценка сложности и неопределённости.

### US-01 — Must — 5 SP

User Story: Преподаватель хочет создать опрос с одним или несколькими вопросами, чтобы собрать мнение студентов.

Критерии приемки: Можно добавить минимум один вопрос; каждый вопрос имеет текст; опрос сохраняется при заполнении обязательных полей; созданный опрос появляется в списке.

### US-02 — Must — 3 SP

User Story: Преподаватель хочет добавлять варианты ответа к каждому вопросу, чтобы студент мог выбрать подходящий вариант.

Критерии приемки: Для каждого вопроса доступно минимум два варианта; пустые варианты не принимаются; дубликаты в пределах одного вопроса выявляются.

### US-03 — Must — 3 SP

User Story: Преподаватель хочет опубликовать опрос, чтобы студенты могли голосовать.

Критерии приемки: После публикации статус становится «Открыт»; для опроса доступна прямая ссылка, которую преподаватель может скопировать и передать студентам.

### US-04 — Must — 3 SP

User Story: Студент хочет открыть опрос по прямой ссылке, чтобы получить доступ к форме без регистрации.

Критерии приемки: Переход по ссылке открывает нужный опрос; если опрос закрыт, показывается сообщение, что голосование недоступно; вход в аккаунт и создание учётной записи не требуются.

### US-05 — Must — 3 SP

User Story: Студент хочет видеть все вопросы опроса и варианты ответа, чтобы понимать, на что он отвечает.

Критерии приемки: Тексты одного или нескольких вопросов отображаются полностью; варианты ответа показаны для каждого вопроса; данные относятся именно к опросу из открытой ссылки.

### US-06 — Must — 5 SP

User Story: Студент хочет отправить ответы анонимно, чтобы его личность не связывалась с выбранными вариантами.

Критерии приемки: После нажатия «Отправить» ответы сохраняются; в таблице ответов не сохраняются ID пользователя, имя, IP-адрес или исходный токен; проверка участия выполняется отдельно по механизму US-09; после успешного сохранения студент видит «Ваш голос учтён».

### US-07 — Should — 3 SP

User Story: Студент хочет видеть список опросов, доступных для прохождения, чтобы находить интересные темы для обратной связи, если у него есть общая ссылка на систему.

Критерии приемки: Отображаются только открытые опросы; закрытые опросы в общем списке визуально отличаются; переход к опросу из списка ведёт на ту же форму, что и по прямой ссылке.

Примечание: В текущей модели API отсутствует признак «публичный». Функция публичной ленты переносится на будущие спринты и не входит в MVP. Доступ к опросу осуществляется преимущественно по прямой ссылке.

### US-08 — Must — 3 SP

User Story: Студент хочет выбрать ответ для каждого вопроса и исправить выбор до отправки, чтобы проверить заполнение опроса.

Критерии приемки: Для каждого вопроса можно выбрать один из доступных вариантов; выбранные варианты сохраняются в форме до отправки; студент может изменить выбор до нажатия «Отправить».

### US-09 — Must — 5 SP

User Story: Студент хочет, чтобы повторная отправка из того же браузера не засчитывалась повторно в рамках одного опроса, чтобы избежать дублирования голоса.

Критерии приемки: При первом открытии опроса сервер выдаёт случайный криптографический токен, если cookie отсутствует, и сохраняет его в cookie с флагом HttpOnly (Secure при HTTPS, SameSite=Strict); сервер вычисляет SHA-256-хеш на основе токена и ID опроса; пара (poll_id, token_hash) записывается в vote_participations с ограничением UNIQUE(poll_id, token_hash); повторный и параллельный запрос с той же парой отклоняется; исходный токен не хранится в базе. Ответы хранятся отдельно от токена. Ограничение действует только для того же браузера с сохранённой cookie и не гарантирует один голос на человека.

### US-10 — Should — 3 SP

User Story: Студент хочет получить понятное сообщение, если отправить ответ нельзя, чтобы понимать причину отказа.

Критерии приемки: При повторном участии отображается сообщение, что голос уже отправлялся; если опрос закрыт, показывается соответствующее уведомление; при отклонении запроса интерфейс не сообщает, что голос учтён.

### US-11 — Must — 3 SP

User Story: Преподаватель хочет закрыть опрос, чтобы прекратить сбор ответов.

Критерии приемки: Статус меняется на «Закрыт»; новые ответы не принимаются; ранее сохранённые ответы остаются доступными.

### US-12 — Must — 5 SP

User Story: Преподаватель хочет видеть количество и доли ответов, чтобы анализировать мнение.

Критерии приемки: Количество участников отображается для опроса целиком; количество голосов и процентные доли рассчитываются отдельно по каждому вопросу; сумма учтённых ответов по вопросу соответствует числу сохранённых ответов на этот вопрос.

### US-13 — Must — 2 SP

User Story: Пользователь хочет видеть статус опроса, чтобы понимать, доступно ли голосование.

Критерии приемки: Статус «Открыт/Закрыт» виден; доступные действия соответствуют статусу.

### US-14 — Must — 3 SP

User Story: Преподаватель хочет открыть результаты выбранного опроса, чтобы изучить ответы.

Критерии приемки: Показываются результаты именно выбранного опроса, количество ответов и распределение вариантов по каждому вопросу.

### US-15 — Should — 3 SP

User Story: Преподаватель хочет опубликовать решение, чтобы сообщить о дальнейших действиях.

Критерии приемки: Текст решения сохраняется и связан с опросом; пользователи могут его прочитать. Решение можно опубликовать только для опроса в статусе «Закрыт». Один опрос может иметь только одно опубликованное решение. Если решение уже существует, повторная публикация обновляет его (PUT), а не создаёт дубликат.

### US-16 — Should — 2 SP

User Story: Студент хочет прочитать решение по опросу, чтобы понимать, как учли обратную связь.

Критерии приемки: Решение отображается рядом с опросом; при отсутствии решения блок не выглядит опубликованным.

### US-17 — Should — 3 SP

User Story: Преподаватель хочет редактировать черновик, чтобы исправить ошибки до публикации.

Критерии приемки: Черновик редактируется; изменения опубликованного опроса не искажают уже собранные ответы.

### US-18 — Could — 2 SP

User Story: Преподаватель хочет отменить черновик, чтобы не публиковать ошибочный опрос.

Критерии приемки: Черновик можно отменить; действие подтверждается пользователем.

### US-19 — Could — 3 SP

User Story: Преподаватель хочет просматривать статистику и управлять опросами с телефона или планшета, чтобы работать с обратной связью вне рабочего места.

Критерии приемки: Экран результатов и список опросов корректно отображаются на узком экране; нет горизонтальной прокрутки; основные действия доступны без увеличения.

Примечание: мобильное прохождение опроса студентом (открытие ссылки, форма голосования, подтверждение) является обязательным требованием основного сценария и входит в критерии приёмки US-04, US-05, US-06, а не в US-19.

### US-20 — Could — 2 SP

User Story: Преподаватель хочет видеть даты создания и закрытия опроса, чтобы ориентироваться в истории.

Критерии приемки: Дата создания и дата закрытия отображаются, если доступны; формат единообразен.

### US-21 — Must — 5 SP

User Story: Преподаватель хочет управлять доступом, чтобы студенты не меняли настройки опроса.

Критерии приемки: Создание, изменение, закрытие и публикация доступны только пользователям с соответствующими правами.

### US-22 — Should — 2 SP

User Story: Пользователь хочет видеть понятное пустое состояние, если опросов нет, чтобы понимать ситуацию.

Критерии приемки: Показано пояснение; преподавателю с нужными правами предлагается создать опрос.

# Согласованные продуктовые решения Sprint 0

Продуктовые решения Sprint 0: основные роли — студент и преподаватель; опрос содержит один или несколько вопросов; основной пользовательский сценарий — публикация прямой ссылки, прохождение опроса, статистика и решение. На первом этапе студент входит в опрос по ссылке без регистрации. В MVP не включаются комментарии, личные сообщения, LMS-интеграции и сложная аналитика. Для ограничения повторного участия выбрано токен-ориентированное анонимное голосование на основе браузерной cookie и хеширования SHA-256. Дополнительные соглашения: (1) студент видит статистику только после закрытия опроса; (2) закрытый опрос отображает статус и решение преподавателя, но не форму голосования; (3) учётная запись преподавателя создаётся администратором заранее, самостоятельная регистрация в MVP не предусмотрена; (4) для демонстрации Sprint 1 используется предварительно созданный тестовый опрос.

### Механизм анонимного голосования (Cookie-based Anonymous Voting)

1\. Генерация токена. Если у браузера ещё нет токена, сервер генерирует случайное криптографическое значение и устанавливает cookie с флагом HttpOnly; для production по HTTPS применяется Secure, а SameSite=Lax ограничивает отправку cookie в сторонних контекстах. Токен нужен только для проверки факта участия, а не для идентификации студента.

При отправке ответа сервер вычисляет SHA-256-хеш на основе токена и ID опроса и сохраняет пару (poll_id, token_hash) в таблице vote_participations. На уровне БД задаётся уникальное ограничение UNIQUE(poll_id, token_hash); проверка и запись участия выполняются атомарно, чтобы параллельные запросы не создали два участия с одной парой. Сами ответы хранятся отдельно и не содержат пользовательский ID, имя, IP-адрес или исходный токен.

Ограничение метода: повторное голосование блокируется только для того же опроса в том же браузере при сохранённой cookie. Очистка cookie, другой браузер или другое устройство позволяют пройти опрос повторно. Поэтому формулировка для документации: «Анонимное голосование на основе криптографических браузерных токенов с хешированием SHA-256 и ограничением повторного участия», а не гарантия «один голос на человека».

Последовательность для UML Sequence Diagram: студент открывает публичную ссылку → сервер возвращает данные опроса и при необходимости устанавливает cookie → студент выбирает ответы и отправляет форму → сервер вычисляет хеш и проверяет уникальность участия → при первом участии сохраняются запись участия и ответы, после чего показывается подтверждение; при повторном участии сервер возвращает отказ без добавления новых ответов.

Минимальные REST-контракты для этого сценария: GET /api/public/polls/{pollId} — получить публичные вопросы и варианты; POST /api/public/polls/{pollId}/votes — отправить выбранные ответы. Для POST предусматриваются успешный ответ после сохранения, отказ для закрытого опроса и отдельный статус/код для уже учтённого участия. Финальные названия маршрутов и кодов фиксируются командой в API-спецификации.

# 12. Критерии приемки инкремента Sprint 1

- Студент открывает опубликованный опрос по прямой ссылке без регистрации.

- В опросе отображается один или несколько вопросов, а для каждого вопроса доступны варианты ответа.

- Ответы отправляются и сохраняются; подтверждение «Ваш голос учтён» показывается только после успешного сохранения.

- При повторной отправке из того же браузера с сохранённым токеном сервер не создаёт повторное участие; в БД действует UNIQUE(poll_id, token_hash).

- При закрытом опросе и повторном участии интерфейс объясняет причину отказа; неуспешная отправка не отображается как успешная.

- В таблице ответов отсутствуют ID пользователя, имя, IP-адрес и исходный токен; токен используется только для проверки участия.

- Команда демонстрирует ограничения метода: другой браузер или удаление cookie могут позволить повторное участие; любой получатель прямой ссылки может открыть опрос, поскольку проверка принадлежности к учебной группе в MVP не предусмотрена.

- Базовый CI/CD проверен: после обновления кода проходит сборка и выполняется публикация прототипа на тестовом хостинге.

- Форма голосования корректно отображается и работает на экранах мобильных устройств (ширина от 320 px), без необходимости горизонтальной прокрутки.

- При открытии закрытого опроса отображается статус «Опрос завершён» и опубликованное решение (если есть); кнопка «Отправить» заблокирована.

- Статистика для студента недоступна до закрытия опроса.

Если результатом является только макет, его нужно называть интерактивным прототипом, а не полностью работающей платформой. Голосование считается готовым только после проверки сохранения ответов, уникального ограничения участия и сценариев отказа.

# Взаимодействие с текущим бэкендом — редакторские примечания

Следующие пункты **не меняют исходное продуктовое ТЗ**. Это зарегистрированные расхождения между новой лабораторной и реализацией API, которую команда проверяла 13 октября 2026 года. Перед реализацией спорного поведения нужны актуальные подтверждения от разработчика бэкенда.

1. **Видимость промежуточной статистики.** Продуктовое ТЗ требует не показывать результаты студентам до закрытия опроса, но доступный серверный `GET /api/polls/{id}/results` был публичным и отвечал на `open`. Скрытие кнопки во фронтенде не является серверным разграничением доступа.
2. **Публикация решения.** US-15 требует разрешать её только для `closed`; текущий серверный `PUT /api/polls/{id}/decision` позволял и `open`, и `closed`.
3. **SameSite.** В US-09 лабораторной стоит `SameSite=Strict`, а в отдельном описании механизма голосования встречается `SameSite=Lax`. Реализованная серверная cookie использует `SameSite=Strict`.
4. **Повторное голосование.** Серверный статус `409` мог означать как повторное участие, так и закрытый опрос; UI не должен обещать определённую причину без надёжного структурированного кода ошибки.
5. **Редактирование и отмена черновика.** US-17 и US-18 есть в продуктовом backlog, но HTTP API для редактирования и удаления созданных опросов отсутствовал. Не изображать эту функцию уже работающей.
6. **Объём первого спринта.** В этой лабораторной Sprint 1 = анонимный сценарий студента + CI/CD (17 SP). В расширенном `Frontend_Sprint1_TZ.md` описан более широкий рабочий релиз. Не путать эти два согласуемых объёма.

# AnonPulse — продуктовые принципы дизайна

**Статус:** рабочее направление, не пиксельный макет.  
**Цель:** единый узнаваемый интерфейс, в котором преподавателю просто создавать опросы и анализировать результаты, а студенту — быстро и спокойно делиться мнением.

## 1. Характер продукта
AnonPulse — современный образовательный SaaS, а не административная система и не маркетинговый лендинг. Впечатление: спокойный, профессиональный, доверительный, визуально чистый, но не скучный. Визуальный стиль должен поддерживать продукт, а не отвлекать от задач.

Ориентиры по принципам, не для буквального копирования:
- **Tally / Google Forms:** понятное создание вопросов без избыточной сложности;
- **Typeform:** ясный фокус внимания при ответе;
- **Slido / Mentimeter:** доступность голосования и наглядные результаты;
- **Linear:** аккуратная плотность информации и визуальная иерархия в рабочих интерфейсах.

## 2. Дизайнерская свобода
Выбирай самостоятельно разумные цвета, шрифты, размеры, сетку, отступы, скругления, компоненты и вариант навигации. Не привязывайся к конкретной палитре или расположению элементов из ранних эскизов. Предложение по стилю — светлая нейтральная база, один выразительный акцент, контрастный текст, последовательные компоненты; тёмная тема не требуется для первого релиза.

Оценка качества — не «сходство с текстовым описанием», а быстрый поиск действия, понятные состояния, читаемость на телефоне и отсутствие визуального шума.

Избегай:
- огромных декоративных hero-блоков внутри рабочего кабинета;
- множества равнозначных primary-кнопок, повторов одного действия;
- искусственных KPI, фальшивой статистики или рекламного текста вместо полезной информации;
- слишком разреженных экранов и чрезмерно крупных карточек при коротких списках;
- перегруженных боковых панелей и сложной навигации без потребности;
- беспричинных градиентов, множества теней, пёстрых цветов и анимаций;
- интерфейсных элементов, которые выглядят рабочими, но не связаны с доступным функционалом.

## 3. Информационная архитектура

### Преподаватель — кабинет
Главная задача: видеть свои опросы, их состояния и быстро переходить к нужному действию. Необходимы:
- список опросов с названием (или запасным названием по первому вопросу), статусом, датой и количеством вопросов;
- понятная возможность создать опрос;
- переход к подробностям, результатам и управлению конкретным опросом;
- пустое состояние, поиск/фильтрация — если улучшают работу без лишней сложности.

Выбор таблицы, компактных строк или карточек — решение дизайнера с учётом ширины экрана. Подробная статистика относится к конкретному опросу. Не подменяй её декоративным дашбордом. `GET /api/polls` не содержит общего числа голосовавших по каждому опросу; не показывай такие числа без дополнительных реальных запросов.

### Преподаватель — создание опроса
Нужна удобная форма с необязательным названием, несколькими вопросами, полевой валидацией и предпросмотром. SURVEY и TEST используют общую композицию конструктора, но настройки оценивания показываются только там, где они нужны. Backend поддерживает одиночный выбор, множественный выбор и текстовый ответ; варианты нужны только для вопросов с выбором. Ясно отделяй редактирование несохранённой формы от созданного на сервере черновика.

Сохранённый черновик можно редактировать: `PUT /api/polls/{id}` полностью заменяет содержимое и настройки. После сохранения обнови карточку данными сервера. Открытый и закрытый опросы редактировать нельзя. Backend умеет удалять собственный черновик с CSRF, но UI удаления не входит в Sprint A.

### Преподаватель — карточка опроса
Покажи статус, структуру опроса и действия по состоянию:
- `draft`: опубликовать;
- `open`: скопировать ссылку, посмотреть промежуточную статистику владельцу, закрыть;
- `closed`: посмотреть итоговую статистику, написать/обновить решение.

Опубликовать можно только из `draft`; закрыть — только из `open`. Для закрытия нужно подтверждение. Размещение управления, просмотра вопросов и статистики выбирай по принципу понятной иерархии, а не максимального числа вкладок.

### Студент — публичное голосование
Доступ по прямой ссылке, без регистрации. Для текущего публичного экрана поддержан старый анонимный SURVEY с одиночным выбором. Backend уже допускает множественные и текстовые ответы, именные SURVEY и TEST; их публичное прохождение относится к следующему спринту. Пока их нельзя отправлять через старую форму.

Приоритет — мобильный экран и минимальная когнитивная нагрузка. Короткий опрос не должен требовать ненужных переходов между страницами. Для длинного опроса продумай индикацию прогресса. Уведомление об анонимности обязательно видно до отправки, не только во всплывающей подсказке. Не обещай абсолютную анонимность.

### Студент и преподаватель — результаты
Показывай реальное число участников, вопросы, варианты, количество голосов и процент каждого варианта; предварительные результаты при `open` доступны только владельцу-преподавателю и администратору, финальные при `closed` публичны. Для сравнения ответов предпочтительны горизонтальные шкалы с текстовыми подписями, числами и доступным контрастом. Возможность обновить результаты открытого опроса — без полной перезагрузки страницы.

Рядом с результатами важен раздел **«Что изменится по результатам»**: опубликованное решение преподавателя. Для преподавателя есть форма сохранения/обновления решения; для студента — чтение. Отсутствие решения отображай честно, без фиктивного контента.

## 4. Поведение и доступность
- Адаптивно: desktop, планшет и телефон; без горизонтальной прокрутки страницы.
- Понятные визуальные состояния: `draft`, `open`, `closed` различаются и текстом, не только цветом.
- Формы имеют подписи, понятные сообщения рядом с полями и видимый фокус клавиатуры.
- Достаточные контраст, размеры интерактивных областей и читаемая длина строки.
- У каждого асинхронного действия — загрузка, успешное завершение и осмысленная ошибка; блокируй дублирующую отправку.
- `404` для отсутствующего опроса, `409` для неактивности/повтора, `429` для лимита запросов: не показывай технические сообщения пользователю без адаптации.
- Никаких персональных данных студентов в публичных результатах; решения отображай как текст, а не как доверенный HTML.

## 5. Как создавать и проверять визуальное решение
1. В настоящем React-приложении реализуй сначала небольшую **переиспользуемую визуальную основу**: навигацию, список опросов, карточку опроса и пример статистики. Допускаются локальные явно помеченные фикстуры только для согласования композиции.
2. Покажи результат в браузере на широком и узком экране. Сам проверь, не слишком ли много пустоты, нет ли повторов действий, легко ли увидеть статус и перейти к результатам.
3. После согласования подключи эти же компоненты к реальному API, а затем последовательно добавляй конструктор, авторизацию, публичное голосование и решение. Не создавай отдельный одноразовый сайт-макет, который придётся переписывать.
4. При последующих задачах сохраняй согласованный визуальный язык, но улучшай композицию по фактическим проблемам интерфейса.

**Критерий успеха:** преподаватель без объяснений может создать опрос и найти статистику, студент — проголосовать с телефона, обе аудитории — понять результат и решение. Дизайн узнаваем, чист и не препятствует этим задачам.
